## 2026-10-28 · v0.7.0 · Inline editor placement and undo recording guard

The inline cell editor now measures its own height (a `ResizeObserver`) instead of reserving 360px for an open option list: it covers its cell from the cell's top, or grows upward from the cell's bottom near the window edge, and follows when the option list opens or closes. Before, a link cell near the bottom opened several rows above its cell and stayed there after a choice. Undo recording now takes a builder that `useUndoHistory` runs inside a try/catch, so a step that cannot be built (for example against an API server started before the batch write returned `archived` and `restored`) is left out of the history with a console warning instead of turning a successful paste, clear, edit, or delete into an error notice.

Validation: `pnpm exec tsc --noEmit`, ESLint and Prettier on the changed files, and the record-grid unit tests (53). Not checked in the browser: editor placement near the window edge, and the guarded path against an outdated server.

## 2026-10-28 · Grid phase 3: undo and redo

Added session undo and redo for grid changes. The batch write gained versioned `archives` and `restores` (archiving keeps the existing reference check, ignoring links from records archived in the same write) and returns `archived` and `restored`, so every step, including deletes and new rows, replays through one atomic, version-checked write. `undoHistory` turns a write into per-record before/after states (`null` meaning archived) and builds the undo or redo write; after each replay, the returned versions update every step in both stacks, so consecutive steps on one record keep working, while changes made outside the history still refuse the step. `useUndoHistory` keeps 50 steps per form, binds Cmd/Ctrl+Z, Shift+Cmd/Ctrl+Z, and Ctrl+Y outside text fields, guards key repeat with a ref, and drops a refused step by identity. Recorded: inline cell edits, paste, cut and paste, clear, saved draft rows, duplicates, and deletes. Grid deletes now go through the batch archive in one write (all-or-nothing, at most 500) instead of one request per record with partial progress. Keyboard help lists undo and redo.

Validation: `pnpm test:api` (archive and restore cases: atomic rollback with an invalid update, stale restore 409, restoring a live record 404, data-preserving restore, reference check and its same-write exception), `pnpm test:web` (history unit tests, including chained versions), `pnpm check`, `pnpm build`, `pnpm lint`, and a Chrome check on a disposable demo database (dropped afterwards): an edit then a paste on one record undone and redone in order; deleting two rows and one undo restoring both in their original positions; undo and redo of a saved new row; an outside PATCH making the next undo refuse without overwriting, with the older step still undoing; Cmd+Z in search staying text undo. Not covered: record editor saves (not recorded), attachment changes, and restore revalidation, so a field that became required after a delete can leave a restored row without it. `crates/persistence/src/records.rs` is at 797 lines, just under the 800-line ratchet.

## 2026-10-28 · Add a record appends an empty row

The Add a record button below the grid now appends an inline draft row at the end and selects its first cell, instead of opening the record editor; it no longer shows the N hint, because N still opens the editor. Insert above/below drafts still block pasting. Delete on the draft row does nothing.

## 2026-10-28 · Grid phase 2, step 3: whole-view loading and row windowing

The web grid now loads every row of a view instead of 50-row pages. `loadRecords` fetches 500 rows per request (the server's per-request maximum rose from 100 to 500), deduplicates records by ID because offset cursors can shift during inserts, merges group counts across pages, and stops at 5,000 rows with a footer notice. A new query shows its first page while the rest loads; a refresh swaps in the complete result at once, so scroll position and cell selection survive saves. The prev/next pager and the `offset` prop are gone. `gridWindow` renders only rows near the viewport from exact fixed heights (47px rows, 40px group headings) and keeps the selected cell's row, the focus row, the edited row, the draft row, and the context-menu row mounted while scrolled away. Group heading rows are keyed by their first record, because group keys repeat while a regrouped view's old rows are still on screen.

Added the `ViewConfig.open_at_end` view setting (default false) and an Open at the last row toggle in the view menu. A view with the setting scrolls to the end once per opened view after the full load. It deliberately selects no cell, because a selected cell takes typed keys such as N. Relation catalogs now fetch up to 500 target records.

Validation: `pnpm check`, `pnpm test:web` (unit tests for loading and windowing), `pnpm test:api`, and a browser check against a disposable database seeded with 832 work logs through the batch endpoint (dropped afterwards). Each 500-row page took about 20ms on a debug server; a 410-record batch create took 0.54s. Measured in the browser: 32 rendered rows out of 832, body height exactly 832 × 47px (also exact with grouping and a collapsed group), Cmd+↓ and arrows keep focus across the window, the anchor row survives scrolling away, refresh keeps scroll position, and the view opens at the last row after saving the setting. Not covered: pasting, which is next, and catalogs for relation targets above 500 records, which still fall back to fetching each missing record.

## 2026-10-28 · Grid phase 2, step 2: atomic batch writes and label resolution

Added `POST /api/v1/forms/{form_id}/records/batch`, which updates and creates up to 500 records of one form in a single transaction. Each update names its expected version. The store checks every version and validates every complete resulting record before writing anything, then checks relation targets during the writes; a stale record (409, listing every stale record) or an invalid one (422, per-record issues in the new `ApiError.records`) rolls the whole batch back. Duplicate records in one batch, empty batches, and batches over the limit are refused up front. Creates append after existing manual order, so pasted rows land below the table. Added `POST /api/v1/forms/{form_id}/records/resolve`, which maps pasted labels to records by exact, case-sensitive primary name in one query and reports match counts, using the same rule as CSV import. `ApiError.records` defaults to empty, so existing clients are unaffected. Regenerated contracts and added web client calls; the CLI does not use these yet.

The API integration test file now has shared `start` and `second_workspace` helpers (behavior-preserving extraction) and a second scenario, `batch_record_writes`, covering: one invalid record rejecting valid updates and creates, a cross-form relation target in a create rolling back the batch, a stale version refusing the batch and naming the record, duplicate/empty/oversized batches, a successful mixed batch with version bumps, appended order and relations, exact/missing/ambiguous/case-sensitive label resolution, and another workspace being unable to write or resolve. Removing the conflict check made the scenario fail.

Validation: `pnpm test:api` (both scenarios), `cargo clippy -D warnings`, `pnpm check`. Single-record writes still validate one record per request; per-record reads inside a 500-record batch are sequential, so a maximal batch may take noticeably longer than a single edit (not yet measured).
